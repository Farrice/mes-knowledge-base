# /high-taste-writing-os - V4 High-Taste Output OS

Use this workflow when Farrice asks for remarkable output, V4-level quality,
high-taste writing, publish-ready work, client-facing strategy, stronger
content, richer research-backed artifacts, or a repair of output that feels
flat, consultant-clean, structurally correct but not alive, or AI-shaped.

Shortcut alias: `/high-taste-os`.

This is a companion OS layer, not a new expert persona. It fuses the existing
High-Taste Writing OS with the V4 Codex preflight standard.

## Operating Wrapper Rule

High taste does not own the answer. It selects the right owner, loads that
owner's files, preserves the V4 chain, and governs the quality gates around the
work.

Use `/high-taste-writing-os` as the operating wrapper when the desired standard
is V4-level output. Do not turn "High Taste" into a persona, expert voice, or
separate taste guru. The final artifact should sound like the right domain owner
doing sharper work, not like a generic high-taste commentator.

## Golden Standard

Always treat these as required references for high-stakes runs:

- V4 golden sample: `_active/linkedin/06-automation/health-performance-ai-search-week-1/publish-copy-v4-codex-preflight.md`
- Repeatability packet: `_active/codex-repeatability/v4-high-taste-output-os.md`

The V4 equation:

`preflight route proof x owner skill loading x golden sample calibration x verified source spine x human thesis x bounded support lanes x adversarial gates x orchestration receipt`

Expert names are never proof. Changed lines, verified claims, reader pull,
specificity, and receipts are proof.

## Modes

Default mode is auto-detect. Explicit flags may be used when the intent is
known:

| Flag | Use When | Output |
|---|---|---|
| `--generate` | Create a new artifact from raw intent | Full artifact plus receipt |
| `--elevate` | Improve an existing draft or prior output | Before/after plus Taste Evidence Ledger |
| `--enrich` | Add proof, research, specificity, or source spine | Enriched artifact plus Claim/Proof Ledger |
| `--audit` | Diagnose only, no rewrite | Failure diagnosis and repair path |
| `--practitioner` | Produce implementation-grade strategy or operator work | Artifact with decisions, acceptance criteria, and handoff |
| `--full` | Maximum chain for public, client, or revenue-critical work | Research/source spine, draft, adversarial pass, gates, finalize |

## Non-Negotiable Boundaries

- Do not publish, post, send, DM, or perform connector writes without approval.
- Do not use paid or quota-heavy tools without cost-gate approval.
- Do not spawn real Codex subagents unless Farrice explicitly authorizes them for this run.
- Do not run parallel rewrites of the same artifact. One composer owns integration.
- Do not invent proof, authority, client results, testimonials, citations, or live AI-search visibility.
- Do not treat this as generic taste training, naming taste, or design taste. Those route to the existing taste workflows.

## Phase 2: Reader Contract

Lock the reader experience before drafting or revising.

| Question | Required Answer |
|---|---|
| Who is this for? | Specific reader and current mental state |
| What should they feel first? | Curiosity, recognition, threat, relief, desire, or surprise |
| What keeps them reading? | One live question |
| What belief should move? | Old belief -> new belief |
| What should they do next? | One action, or no action for pure thought leadership |

If this table is weak, gather better material before writing.

## Phase 3: Material, Source, And Proof Ledger

Do not try to sound better before the material is better.

Treat a source gap at the smallest claim, scene, or causal bridge. Retrieve,
label, narrow, omit, or use a visible placeholder; do not refill the gap with
plausible language. Supported adjacent work continues.

Required material:

- one private sentence from the reader or buyer
- one concrete image, scene, artifact, or moment
- one proof or demonstration moment
- one thing the piece refuses to say
- one sentence that could only come from Farrice's taste or worldview
- one tension pair: market story vs private reader reality

For factual or public claims, create a Claim/Proof Ledger:

```markdown
## Claim/Proof Ledger
| Claim | Status | Source/Proof | Use In Draft |
|---|---|---|---|
| [claim] | VERIFIED / LIKELY / UNCONFIRMED | [source or limit] | yes/no |
```

Browse or research when claims may have changed. If live verification was not
run, mark claims as `UNCONFIRMED` or remove them.

## Phase 5: Architecture Map

Build the artifact before polishing it.

| Layer | Decision |
|---|---|
| Hook | First line creates a real question or private recognition |
| Rehook | Every 6-8 lines renews the reason to continue |
| Proof path | Claims are followed by artifact, example, consequence, or mechanism |
| Emotional order | Reader feels seen before being taught |
| Turn | One meaningful shift in how the reader sees the problem |
| Residue | Final line or next action leaves a phrase, image, or action behind |

## Phase 6: Compose Once

Write one draft in one voice. Do not paste together expert outputs.

Required qualities:

- one controlling thesis
- one concrete scene or lived pressure point
- buyer/audience relevance
- proof near claims
- conversational movement
- varied paragraph rhythm
- natural offer, decision, or handoff path

Avoid:

- repeated single-line cadence
- generic value-post sequencing
- "not X, but Y" patterns as a crutch
- clean consultant summaries
- CTA theater
- visible expert/framework labels inside the artifact

## Phase 7: Bounded Support Lanes

Use at most three support lanes per pass. Each support lane must name its job
before contributing.

| Failure | Support Lane |
|---|---|
| Clear but lifeless | Nicolas Cole EDAN, then Roth erosion |
| Logical but boring | Kallaway reader-pull/rehook |
| Correct but hollow | Nate hollowness forensics and material infusion |
| Too safe or average | Jacoby pattern/invention pass |
| LinkedIn-specific | Lara Acosta buyer/amplifier and scan path |
| Personal voice or serial story | Fresh Voice System |
| Zero-proof client acquisition | Nicolas Cole Client Acquisition |
| Converting copy | Copywriting owner plus publishable copy gate |

Each lane returns only:

- top 1-3 issues
- exact changes suggested
- what to preserve
- what to cut
- remaining risk

The main composer integrates. Support lanes do not own the final voice.

## Phase 8: Adversarial Pass

Before final delivery, ask:

- Which lines sound consultant-clean?
- Is the wound too abstract?
- Are the stakes too polite?
- Did proof become decoration?
- Does the format feel like AI learned LinkedIn?
- Is the CTA or next step asking for trust too early?
- Is the output impressive by receipts, not expert names?
- Did any craft pass invent or promote a fact, scene, causal bridge, outcome,
  or permission beyond the available source? If so, repair that unit without
  suppressing supported adjacent work.

**The enchantment check** (added 2026-08-06 from the Forsyth forge — two questions, both falsifiable):

- **Read it aloud.** Does any line survive being spoken — or does the tongue stumble, the breath run out, the prose flatten into monotone? Memory runs on sound; a piece that cannot be read aloud will not be remembered.
- **The misquote test.** Take the one line this piece most needs remembered. Would someone who heard a flat paraphrase "correct" it *into* your line? If not, the line has no shape, and the fix is a figure — not more adjectives. Route to `/enchant elevate` or `skills/mark-forsyth-rhetoric/workflows/07-figure-diagnostic.md`.

A structurally correct, consultant-clean, entirely unquotable draft passes every other gate on this page. These two catch it.

Apply fixes before verification.

## Phase 9: Verification And Finalize

Use relevant gates based on artifact type.

For public, revenue, content, copy, or client-facing prose:

```bash
python3 execution/content_finish_gate.py check --file [artifact] --label [label]
python3 execution/prose_classifier.py check [artifact]
python3 execution/grounding_guard.py [artifact] --task-type Content --strict
```

Finalize substantial deliverables with the actual artifact file:

```bash
python3 execution/chain_runner.py finalize "[what was produced]" \
  --expert [owner] --skill [skill] --workflow high-taste-writing-os \
  --type [Content|Strategy|Research|Client Work|System|Creative|Analysis] \
  --intent [1-10] --expert-score [1-10] --adversarial [1-10] \
  --sub-agents 0 --anchor-named --source-request "[raw user request]" \
  --content-file [artifact] \
  --notes "platform: codex | Verification: [PASS/PARTIAL/FAIL]"
```

If a local gate disagrees with chain finalize, report the disagreement plainly.

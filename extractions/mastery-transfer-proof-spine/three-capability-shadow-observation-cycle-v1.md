# Mastery Transfer Proof Spine — Three-Capability SHADOW Observation Cycle v1

## Verdict

Run one bounded, three-capability observation cycle across an operating system,
a creative-judgment system, and a control-plane companion. The object under
observation is the **Mastery Transfer Proof Spine**, not the maturity of the
three capabilities.

The cycle may conclude `KEEP_SHADOW`, `REVISE_SHADOW`, or `RETIRE`. It cannot
promote the spine, change a capability's canonical proof state, create runtime
enforcement, or add a mandatory extraction step.

## Why These Three

| Capability | Task type | Conservative starting state | First unearned state | Proof-inflation temptation |
|---|---|---:|---:|---|
| Oren Funnel-Flywheel | Commercial operating strategy | `TRANSFERRED` | `GENERALIZED` | Treat two development-visible cases as held-out generalization or market readiness. |
| David Perell Idea-to-Culture | Creative judgment and writing | `RUNNABLE` | `TRANSFERRED` | Treat 18/18 detached runtime fixtures or an unjudged blind pack as embodiment, recognition, or A-tier preference. |
| Systems-Thinking Overlay | Control-plane advisory behavior | `TRANSFERRED` | `GENERALIZED` | Treat three retrospective cross-task replays as prospective causal lift or promotion readiness. |

This set creates three different failure opportunities: development-example
inflation, runtime-to-taste inflation, and retrospective-to-causal inflation.
Three adjacent marketing capabilities would not test the spine this hard.

## Observation Question

When the same frozen capability evidence is assessed with and without the
Mastery Transfer Proof Spine, does the spine materially improve at least one of
these decisions without creating burden or reducing useful range?

1. claim boundary;
2. next test design;
3. next evidence action;
4. safe-use boundary;
5. preservation or recovery boundary.

If none changes, the spine should remain silent and the observation should be a
tie, not a ceremonial treatment win.

- Status before execution: `DESIGNED_NOT_RUN`.

## Cycle Protocol

### Phase 0 — Freeze

1. Freeze the evidence paths, exact prompts, preservation locks, starting proof
   states, and evaluation fields in
   `three-capability-shadow-observation-cycle-v1.json`.
2. Keep answer keys and treatment mappings unavailable to the evaluator.
3. Do not add evidence after either arm has begun. New evidence goes into a
   later cycle.
4. Record all event counters as zero before generation.

### Phase 1 — Native Baseline Arm

For each capability, give a fresh runner only the frozen evidence packet and
the capability's native proof tools. Ask for:

- strongest supportable claim;
- current proof state;
- first missing proof;
- next evidence action;
- safe-use boundary;
- preservation locks.

Do not expose the Mastery Transfer ladder, its state names beyond those already
present in the source packet, or the expected treatment delta.

### Phase 2 — Spine Treatment Arm

Give a different fresh run the identical evidence packet plus
`mastery-transfer-proof-spine.md`. Require the same output fields. The treatment
may not use evidence unavailable to the baseline arm.

### Phase 3 — Safe-Use Negative Control

For each capability, ask for a bounded internal use that does not claim a state
above its current evidence. The spine passes this control only when it allows
the nearest safe use without extra questions, mandatory fields, or promotion
language.

### Phase 4 — Blind Comparison

1. Normalize both arms into the same headings and remove route, file, state-name,
   length, and formatting tells that reveal the arm.
2. Precommit A/B mapping before judgment.
3. Use an evaluator who did not build either arm.
4. Judge the pair on material decision quality, not verbal sophistication.
5. Record `TREATMENT_WIN`, `BASELINE_WIN`, or `TIE` with the decisive reason.

The builder cannot self-grade this phase. A result remains `PENDING_EVALUATOR`
until Farrice or another explicitly authorized independent evaluator records it.

### Phase 5 — Burden And Preservation Audit

For each capability, record:

- added operator questions;
- added mandatory fields;
- safe uses blocked;
- native owner displaced;
- creative or strategic range reduced;
- unsupported proof-state upgrade;
- material decision changed;
- smallest useful delta;
- whether no change would have been better.

### Phase 6 — Cycle Verdict

Apply the precommitted verdict rules below. Do not rewrite the rules after
seeing the results.

## Precommitted Cycle Verdict Rules

### `KEEP_SHADOW`

All must be true:

- treatment preferred on at least two of three capabilities;
- no baseline win;
- at least two material changes across claim boundary, test design, next action,
  safe-use boundary, preservation, or recovery;
- zero proof-state inflation;
- zero false blocks on the three safe-use controls;
- zero native-owner displacement;
- zero added questions on the fully specified packets;
- David's creative range and Farrice's taste authority preserved; and
- at least one independent blind-preference receipt recorded.

This verdict means only: continue observing the spine in SHADOW mode.

### `REVISE_SHADOW`

Use when there is one treatment win, one isolated burden or preservation miss,
or a useful delta that is too generic. Change only the smallest failing rule,
then rerun the affected capability and its safe-use control. One repair pass
maximum.

### `RETIRE`

Use when any is true:

- zero treatment wins;
- two baseline wins;
- repeated false blocks or question burden;
- the spine displaces native craft owners;
- it produces the same generic evidence recommendation for all three cases; or
- it encourages proof-state inflation.

Archive the observation design; do not delete the underlying capability proof.

## Agentic Engineering Packet

- **Objective:** Learn whether the spine changes proof decisions across three
  dissimilar capabilities without becoming process theater.
- **Source truth:** Only the frozen paths named in the cycle manifest.
- **Context plan:** Load one capability packet at a time; never bulk-load all
  expert material into an arm.
- **Work chunks:** Freeze → baseline → treatment → safe-use control → blind
  judgment → burden audit → verdict.
- **Review loop:** One three-capability cycle; one repair pass maximum.
- **Dependency gate:** No new dependency or external service.
- **Structure pass:** Confirm no router, hook, command, hot skill, or mandatory
  schema was added.
- **Use-now artifact:** This design and its frozen JSON manifest.
- **Hardening proof:** Existing proof tools, human blind receipts, JSON syntax,
  path checks, and no-regression review.

## Systems-Thinking Trace

- **Wider outcome:** Make extraction intelligence trustworthy in live decisions,
  not merely impressive in local builds.
- **Assumption changed:** Three receipts are useful only if they span different
  proof-inflation pressures and compare against a real native baseline.
- **Craft owner:** The native capability owner certifies usefulness; Farrice or
  another independent evaluator owns blind materiality and taste.
- **Paved default:** One frozen assessment shape and verdict rule, with a bounded
  capability-specific last mile.
- **Outcome owner:** `/source-to-skill-system` owns the observation design;
  Farrice retains promotion authority.
- **Learning decision:** A clean cycle can justify more SHADOW observation, not
  enforcement.
- **Remaining risk:** Evaluator availability and leakage from prior familiarity
  with the three systems.

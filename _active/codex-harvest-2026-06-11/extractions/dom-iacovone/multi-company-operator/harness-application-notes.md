# Harness Application Notes

## Why This Enriches Antigravity

The video is useful because it gives the harness concrete entrepreneurial examples instead of abstract systems language. It helps future agents see how operating models behave under real constraints: finance, product, meetings, retail timing, valuation, channel incentives, and founder behavior.

## Source-To-Skill Usage

Use this package as an example corpus when `/source-to-skill-system` needs to decide whether a source deserves:

- a reference only,
- a focused skill,
- a workflow command,
- a companion OS layer,
- or a business asset.

This source earned a focused skill because it has more than six reusable mechanics across more than three chapters, plus clear business application surfaces.

## Control-Plane Analogy

| Business Mechanic | Harness Analogy |
|---|---|
| Four SGM blocks | Keep source-to-system builds in a few coherent components. |
| Weekly finance truth | Verify with scripts and evidence, not confidence. |
| Stage-gate innovation | Gate new skills by distinct need, better mechanism, maintainability, and route fit. |
| Delegate/elevate | Let each workflow own its function instead of routing every decision to one mega-command. |
| Retail lag | Some system changes only show value after discovery, use, and validation. |
| Trade spend leakage | Dead wrappers, stale registries, and duplicate routes create hidden operating drag. |
| Buyer mistake | User-requested artifact shape should not override the user's real objective. |
| Onside exception | Defaults can be overridden when source evidence and context support the exception. |

## Integration Boundary

The new skill should remain cold/on-demand. It should not compete with `/source-to-skill-system`, `/extraction-governor-agent`, `/autopilot`, or `/system-audit`. Those remain control-plane owners.

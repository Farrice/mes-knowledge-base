# Naming Conventions

Use this project naming standard for every new file in this folder.

## Folder Slug

`2026-06-23-revenue-source-to-search-trust-layer-glp1`

Pattern:

`yyyy-mm-dd-[domain]-[specific-object]-[outcome-or-proof]`

This folder uses:

- `2026-06-23` because the offer layer was organized on June 23, 2026
- `revenue` because the work is offer, service ladder, client acquisition, and proof
- `source-to-search-trust-layer` because that is the named module
- `glp1` because GLP-1 Movement Receipt is the first proof demo

## File Pattern

Use:

`yyyy-mm-dd-[project-or-asset]-[artifact-type].md`

Examples:

- `2026-06-23-source-to-search-trust-layer-one-page-offer-insert.md`
- `2026-06-23-glp1-movement-receipt-public-demo.md`
- `2026-06-23-source-to-search-trust-layer-adversarial-review.md`
- `2026-06-23-glp1-movement-receipt-5-page-audit-sample.md`

## Artifact Type Terms

Use these endings:

- `one-page-offer-insert`

## Versioning

If a file gets materially revised, keep the date and add a version:

`2026-06-23-glp1-movement-receipt-public-demo-v2.md`

Use `legacy-draft` only for older drafts preserved for comparison.

## Metadata

Substantial artifacts should get a sidecar:

`[same-file-name].metadata.json`

The metadata should include:

- `title`
- `artifact_type`
- `created`
- `workspace`
- `project_slug`
- `source_files`
- `status`
- `publish_boundary`

## Status Labels

Use these exact status labels in project docs:

- `working`
- `internal_review_ready`
- `warm_buyer_ready`
- `public_demo_ready`
- `needs_original_proof`
- `publish_blocked`
- `archived_legacy`

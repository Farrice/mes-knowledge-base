# rationale — portrait-statement-cta

## ① Form + tree-path-with-why

form: a-framed-image

- **Q1 (solid-color, zero texture, no image?) — NO.** `image_zone.exists = true` — there is a real
  photographic portrait on the canvas. The overall canvas background OUTSIDE the photo is a flat
  uniform `#F3F3F0` (canvas grey, brand `colors.bg_light`, eyedropper-flat, zero grain/gradient), but
  Q1 requires BOTH zero texture AND no image at all — the image disqualifies it immediately. Tree
  continues.
- **Q2 (blank in-scene SURFACE holding content — screen/frame/paper/billboard)? — NO.** The photo is
  not a blank surface waiting for baked content; it is itself the finished content (a real studio
  portrait of Farrice, fully populated). There is no screen, no signboard, no paper placeholder
  anywhere in the ref. Tree continues.
- **Q3 (image contained in a rectangle, not full-bleed)? — YES → STOP, form = a-framed-image.** The
  portrait sits in a bounded rectangle roughly `left 84px / top 150px / width 912px / height 560px`
  on the 1080×1350 canvas (≈7.8%, 11.1%, 84.4%, 41.5%). A DIFFERENT material — the flat `#F3F3F0`
  canvas — is visible on all four sides of the photo (top margin above it, side margins left/right,
  and a large open band below it before the headline starts). The photo's own texture (studio wall,
  window-blind light pattern) does NOT continue past its rectangle edge — this passes the Q3 hard-edge
  test cleanly (it is not a full-bleed scene disguised as a "framed" region; the frame is real). The
  tree stops here per "first match wins."

`text_placement: outside-image` confirmed — every text block (masthead row, headline, subtitle, CTA,
footer) sits OUTSIDE the photo rectangle, on the flat canvas, in its own clean bounded zone. None of
the text touches or overlaps the photo.

## ③ Pipeline

edit_mode: **none** — this deviates from `scenarios/a-framed-image.md`'s stated default for a "fixed
image" ("generate 1× at setup via edit-from-ref, store as static asset"). Here, NO AI generation touches
the photo at all, at any point, ever. Reason: `tokens.json > portrait_policy` is a hard brand rule —
`allowed: ["crop","uniform scale"]`, `prohibited: ["face regeneration","replacement","inpainting",
"reshaping","beauty filtering","face-specific color alteration","AI upscaling","synthetic portraits"]`,
and move #9 ("Original portrait") states the portrait must be "Farrice's original, unaltered portrait...
no beauty edits, synthetic generation, creator-lifestyle props, or AI upscaling." Even a single
edit-from-ref pass at setup would violate this — `edit-from-ref` re-renders the pixels through the image
model, which is exactly the "regeneration" the policy forbids. The correct pipeline is: use the REAL
supplied photo file verbatim (crop + uniform scale only, both done by CSS `object-fit:cover` +
`object-position`, zero pixel regeneration), sourced from
`_active/farrice-brand/farrice-creative-strategist-portfolio/assets/farrice-studio.jpg` (the exact
file the ref's own authoring HTML references — `visual-identity/compositions/editorial/frames/
07-portrait-close.html` line 7: `<img src="../../../../../_active/farrice-brand/
farrice-creative-strategist-portfolio/assets/farrice-studio.jpg">`), copied into
`assets/photo-main.jpg` for this template and bound as `{{PHOTO_MAIN_PATH}}`.

when_ai_runs: **never** — this template ships with zero `[ai-image-zone]` blocks and no `_ai_bg/`
directory. There is nothing to generate at setup or per-post; a future post that swaps the photo would
supply a DIFFERENT real photo file (still governed by the same portrait_policy), never an AI render.

extraction: nothing is extracted or cleaned. The photo is placed as-is (a direct file copy, re-encoded
losslessly-equivalent by Pillow, zero content change). All text blocks (kicker, date, headline,
subtitle, CTA, footer ×4) become HTML `data-slot` zones on the flat canvas-grey background
(`background: var(--brand-bg-light, #F3F3F0)`), authored as CSS, no cleaning needed since there was
never a baked-text scene to begin with.

## ④ Ambiguity (examined)

**Was this ref actually B1 (in-scene surface) instead of A?** No — ruled out. B1 requires a BLANK
surface (screen/frame/paper/billboard) that the AI fills with content inside the scene. The photo here
is not blank and not a placeholder surface; it is the finished photographic content itself, and none of
the surrounding text lives ON the photo (it all lives outside it, on the flat canvas). B1 does not apply.

**Could the mid-canvas gap (photo bottom ≈52.6% to headline top ≈57%, then headline to subtitle
≈62.5%→74.8%, and the large open band below the footer's CTA down to the footer strip at ≈95.3%) be a
sign this should route to B2 (reserved-zone) instead of A?** No — B2 is for a *generated scene* that
reserves a clean band for HTML text; here there is no generated scene at all outside the framed photo —
the "reserved zone" is simply flat canvas-grey CSS background, which is exactly what Form A's "text
lives outside the contained rectangle, in a clean HTML zone" already describes. Inventing a B2 read
would incorrectly imply a bg image/texture needs generating; it does not — `background: var(--brand-
bg-light)` is sufficient CSS, per the "Background route decision" solid-color test (uniform hex,
zero gradient, zero noise, zero grain — canvas grey passes this cleanly).

**Should `subject_role` have been forced into `fixed-hero` or `free-subject` to match the two canonical
values?** Examined and rejected both. Forcing `fixed-hero` would imply the per-post prompt "recolors the
ref" (rule 7) — but there is no per-post PROMPT at all here (edit_mode: none), so "recolor" doesn't
apply; the photo pixels never regenerate, period. Forcing `free-subject` would imply "change the subject
to `{PHOTO_SUBJECT}`" is correct behavior — but that is explicitly the class of error `tokens.json`
prohibits (synthetic portrait generation) and would produce a random AI-invented face standing in for
Farrice, which is worse than either canonical case. The honest read is the third category recorded in
§2: a real, brand-owned, policy-locked identity photo, swappable only by hand with another real photo of
the same person, never by AI. This is a genuine gap in the standard `fixed-hero | free-subject`
dichotomy for portrait-governed brands, and it is resolved conservatively (favoring the strictest
non-generation reading) rather than forced into a mismatched category.

**Is the top-left "Creative Teardown" + date row the brand's `chrome.masthead` (and therefore locked per
`tokens.json > locked_fields`)?** Examined and rejected. `tokens.json > chrome.masthead.labels` is
`["FARRICE CAIN", "", "CREATIVE STRATEGY FOR SUPPLEMENT + PERFORMANCE BRANDS"]` (master-brand mode) or
`["THE ANGLE MAP", "", "FARRICE CAIN"]` (offer mode) — neither matches what this ref actually shows
("Creative Teardown" / a date). The pool's `styles.json` and `REVIEW-NOTES.md` document TWO separate
visual grammars sharing one pool: `typographic` (which uses the literal `chrome.masthead` values, seen
in `statement-close-cta`/`headline-subline-cover`) and `editorial` (this ref's style, a Canva-inspired
"header title + date + arrow / footer strip" grammar where the header carries a per-post CATEGORY label,
not the fixed brand wordmark). Since this ref is `editorial`-style and its header content literally
differs from the `chrome.masthead` token values, it is authored as an ordinary editable content slot,
not injected chrome. The brand's actual identity signature in THIS grammar lives in the FOOTER instead
("Farrice Cain" · domain), which is authored as fixed elements for that reason.

**Does the render pipeline's standard `visual-identity/headshots/` convention apply here?** Examined —
no such directory exists in this brand_context (`brand_context/visual-identity/headshots/` is absent).
The real portrait asset instead lives in a project-specific location
(`_active/farrice-brand/farrice-creative-strategist-portfolio/assets/farrice-studio.jpg`), discovered
via the ref's own authoring source HTML rather than the standard headshot folder. This template copies
that file into its own `assets/photo-main.jpg` rather than depending on the non-standard external path
at render time, so the template stays self-contained and portable. Check F (face-match) is not wired up
for this template for the same reason (no `visual-identity/headshots/<file>` to compare against) — noted
so a reviewer doesn't expect that gate to fire.

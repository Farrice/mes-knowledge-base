# Workflow 01 — ve-audit-offer

> **Produces**: A paid Knowledge-Base Audit — the client's spine, a 7-datapoint knowledge map, a findings sheet sorting everything into on-fire / outdated / disconnected, and a scoped build proposal the client can say yes to. The audit output IS the scope.
> **Load first**: [genius.md](../genius.md) + `skills/simon-intellectual-library-os/genius.md`
> **Stacks**: `/library-retrieval-audit` (technical scoring backbone — run it UNDER this for the compounding-test axes; this workflow wraps it in the sell-side spine + findings + proposal).

## Role
You are Adam Sandler running the entry audit that opens a KB engagement. Adam: *"when these engagements are beginning, there's a huge opportunity for an audit."* The audit does double duty — it maps the knowledge AND it becomes the scope. You are not building the KB yet; you are producing the artifact that makes the client see their own mess and buy the fix.

## Pre-Flight Gate
- Confirm this is an ENTRY engagement (diagnostic, pre-build). If a KB already exists and you're scoring its retrieval health, that's `/library-retrieval-audit` standalone — come back here for the sell-side wrapper.
- You need access to (or a described inventory of) the client's existing knowledge: docs, transcripts, brand guidelines, wherever it lives.
- Expect mess. Adam: *"you're jumping into a messy pool and you got to clean it all up."* Do not pre-tidy the client's story.

## Skill Acquisition
Read `genius.md` §Pattern 2 (the paid audit) + §Anti-Patterns. Read `simon-intellectual-library-os` `/library-retrieval-audit` for the four-axis compounding score — you'll run it as the technical layer and fold its findings into the on-fire/outdated/disconnected buckets.

## Execution — FROM THE SOURCE
1. **Ask the spine question** (Adam's kickoff, verbatim): *"Okay, let's talk about your spine... What is the one thing that everything else in the business sort of like ladders up to? And usually that is a goal or an objective."* Phrase it plainly to the client: *"what is the driving force of this company?"* The answer anchors everything.
2. **Map the 7 baseline data points** around the spine. Adam: *"I do have some material that lays out a baseline set of schema. There's seven different data points, basically. And this is usually enough to get going."* Default marketing-flavored set (tune to the business): (1) Company/Business Profile, (2) ICPs / audience, (3) Positioning, (4) Differentiation Strategy, (5) Messaging Framework / Content Pillars, (6) Visual Identity, (7) Voice & Tone. For a non-marketing department, swap the seven for that domain's spine-supporting entities (an accounting KB ≠ an SEO KB).
3. **Run the messy pile** — locate where each data point actually lives, what's missing, what conflicts. Adam: *"knowledge is going to be messy."*
4. **Sort every finding into three buckets** (Adam's own triage): **ON FIRE** (broken, actively wrong), **OUTDATED** (*"here's a brand guideline from 2020, 5 years ago"*), **DISCONNECTED** (*"connections that were not obvious"*). Surface at least one insight the client didn't know: *"did you know this and that?"*
5. **Layer the compounding score** — run `/library-retrieval-audit`'s four axes (connection / contradiction / freshness / provenance) and note the retrieval gap as extra scope justification.
6. **Write the scoped build proposal** — from the audit, the KB scope is now obvious: here's your spine, here's your seven data points, here's what's on fire/outdated/disconnected, here's the KB we build and in what order. Route the build to `ve-scaling-path` (substrate) + `ve-client-ui-layer` (packaging).

## Content Type Adaptations
| Client type | Adaptation |
|---|---|
| Marketing team / agency | Use the default 7 (profile/ICP/positioning/differentiation/messaging/visual/voice) |
| Single department (accounting, SEO, ops) | Replace the 7 with that domain's spine-supporting entities; note cross-department integration as later scope |
| Solo founder | Spine = the founder's core objective; lighter 7, personal-brain scope |
| Prospect with an existing "AI brain" | Lead with the `/library-retrieval-audit` four-axis fail, then wrap in spine + proposal |

## Output Requirements
Deliver a one-artifact audit: **Spine** (the one thing everything ladders to) + **7-datapoint knowledge map** (each point: where it lives / present-missing-conflicting) + **Findings sheet** (every item tagged ON FIRE / OUTDATED / DISCONNECTED, ≥1 surfaced insight) + **Retrieval score** (four-axis, from `/library-retrieval-audit`) + **Scoped build proposal** (KB scope + build order + routed next workflows). Refuse the word "easy"; say "straightforward." The client should see their own mess and the fix in one document.

Execution prompt: references/prompts-v2/viable-edge-kb-audit.md — honor its Output Contract.

## Quality Gate
- Did you open with the spine question and anchor the map to a single driving objective?
- Are all 7 data points located (present / missing / conflicting), not assumed?
- Is every finding sorted into on-fire / outdated / disconnected, with ≥1 non-obvious insight surfaced?
- Did you run the `/library-retrieval-audit` four-axis score as the technical backbone (not reinvent it)?
- Does the audit DOUBLE as the scope — is the build proposal a direct read-off of the findings?
- Anti-Pattern check (`genius.md`): no RAG/vector recommendation for a small-doc client; no "easy"; no company-scale bite if the buyer is nervous (route to `ve-department-wedge`).

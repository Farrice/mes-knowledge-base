# Context-Engineering Build (End-to-End) (`/ce-build`)

You are operating from Chase Hughes's one move, restated as a build instruction: **stop engineering the outcome, engineer the conditions upstream of it, and the outcome becomes an automatic, self-chosen byproduct.** This is the whole machine running at once. You take a real objective and produce the deferred-ask context that makes the behavior inevitable, then hand each asset to the expert who writes *into* the designed context instead of pushing the outcome directly. Milgram is the proof the contract is built on — no script, *"just a dude in a lab coat,"* engineering the conditions that made shocking a stranger permissible. A Context-Design Spec is the deliberate, ethical, logged version of that lab coat.

You are not teaching context engineering here. You are doing it. The deliverable is a finished spec a production expert can build from without asking you a single question — the test of a real spec, not a described one.

## When This Fires

Run this workflow whenever:
- A request names an objective + an audience + channels and wants the *whole* build, not a single component ("design a launch where buying feels automatic," "build the context for a $5K offer to invisible-expert founders")
- A multi-deliverable marketing or creative mission needs one coherent context underneath every asset so the copy, the video, and the LinkedIn post all build the same recipient instead of pushing three different outcomes
- You catch yourself (or a teammate) reaching for a better hook/close/script — the instinct to optimize the visible outcome is the exact signal that `/ce-build` should run first and produce the upstream context the assets write into
- A `/supercomputer` mission is being staged and needs an anchor-memory-grade context spec to keep cross-phase cohesion (stack the two: `/ce-build` emits the context, `/supercomputer` carries anchor memory + the cost gate across the deliverables)

**Precedence rule:** a request like "design a campaign where buying feels automatic" routes to `/ce-build` **first** to emit the context, which *then* hands off to the production bindings (copy → Luke Iha; LinkedIn → Lara Acosta; cold video → `/caleb-4c-intro`; multi-deliverable → `/supercomputer`). `/ce-build` produces the *context*; the production workflows produce the *assets*. Never let a production workflow run first and reverse-engineer the context — that is "say the thing more persuasively," which is the failure mode of the whole domain.

## Execution

Run all eight stages in order. Each stage produces a real design decision, not a description of the target. An empty field is a decision you skipped, not a field that did not apply.

### Step 1 — Lock the Three Inputs (then resolve to never push the ask)

Confirm the three required fields. If any is missing, the build is flat:

- **Desired end-state** — the one behavior you want automatic, phrased as a verb the target performs ("founder books the diagnostic call"), not an outcome you receive ("more bookings"). One sentence. Two sentences = two end-states = two specs.
- **Target** — who the recipient is: their current perception, the category they think they are in, their installed source-code if known (the 8-year-old diagnostic: *"What did you do to get friends, safety, rewards?"*).
- **Channels** — every delivery surface in play. You cannot grade followability or hesitation without one.

Lock the end-state sentence in a drawer. The ask phrased as a push **never appears in the spec.** It is deferred to a single touchpoint (Step 5) and arrives after the recipient is built, so it lands as the recipient's own conclusion.

### Step 2 — Trace the Condition Chain (the Upstream Engine)

*"Upstream Engine" is the extractor's synthesis coinage — not a phrase Hughes uttered.* Hughes's verbatim contrast is the law: *"if you're good, what you engineer are conditions. And if I can engineer the right conditions, I can get you to do anything. Anything… make the person the perfect recipient for what I need to give them."*

Trace backward from the end-state, asking the planning verb at each rung — *"What is upstream of this?"* — until you hit a condition you can actually build through the channel.

```
END-STATE: [the verb]
  ↑ upstream: what permission must already be live for that verb to feel obvious?
  ↑ upstream: what category/context makes that permission make sense?
  ↑ upstream: what perception shift puts them in that category?
  ↑ upstream: what state must they be in to accept that perception shift?
  ↑ upstream: what installed source-code does that state ride on, if known?
```

Build the lowest rung you can reach first; the higher rungs fall out for free. The absence of an early ask in the chain is correct, not weak — the master-operator signature is how long you can defer the ask while the chain installs.

### Step 3 — Map the Ambient Forces (what is already acting on the recipient)

Before adding a single force, map the forces already in the room. The target arrives mid-fractionation, mid-feed, pre-categorized by something. Mark each PRESENT / ABSENT / UNKNOWN and note its direction:

- **FEAR loop** (Focus → Emotion → Agitation → Repetition). Is the channel itself a fractionation surface (a feed, a high-pressure sales floor)?
- **Fractionation** (Erickson). Is the target arriving wrung-out from up-down cycling elsewhere — more GABA, higher theta, pliable? (The "works through a screen, no hypnotist present" logic is a **synthesis inference, LIKELY not Hughes-verbatim** — carry it as an inference.)
- **Engineered division / prepackaged enemy.** Has the target already been handed an enemy and told how to feel? Destabilization drops critical thinking ~50% and raises suggestibility ~10x — the thornbush-grab state. (Source hedged by Hughes: *"I think it's called Unrestricted Warfare,"* by *"two Chinese intelligence officers."* Carry the hedge.)
- **Algorithm** (Stuart Russell / *Human Compatible*). Is a recommender narrowing the target's preferences toward predictability? *"The feed gets me so well"* is the symptom of capture.
- **Installed source-code.** What childhood app-turned-source-code is running? The most concealment-burdened recipient is the most pliable.

The force-map's job is honesty: if the target arrives already destabilized, the spec must declare whether it **reduces that chaos and supplies clarity (help)** or **rides the chaos to sell the cure (BLOCK at Gate Test 5).**

### Step 4 — Design the PCP Engine (Perception → Context → Permission)

PCP is Hughes's real acronym. *"All I have to do is it's a PCP formula. I change your perception about the situation… if I shift category and context, that changes what you think you're allowed to do… Permission is that final thing that says, 'Oh, in this context I'm completely allowed to do this and it makes perfect sense.'"* Three sub-fields, in his order:

- **Perception shift** — state the before and the after. What does the target currently believe is happening / possible, and what is the new perception?
- **Category word** — the single loaded word that reclassifies the situation. Category beats argument. *Pick the one word and write it down.* The pub operator's ethical version is canonical: *"he shifted the context to her being helped instead of controlled."*
- **Permission statement** — finish the sentence the recipient should be able to say in their own head: *"in this context I'm completely allowed to ____ and it makes perfect sense."* If you cannot write it cleanly, the category word is wrong.

### Step 5 — Build the Recipient (touchpoints + install order + deferred ask)

List the touchpoints in the order they fire. At each, declare which layer it installs (belief → identity → permission, in that order) and confirm the ask is NOT there. Then name the single touchpoint the ask is deferred to.

```
Touchpoint 1 (channel: ___) → installs: [belief] → ask present? NO
Touchpoint 2 (channel: ___) → installs: [category/context] → ask present? NO
Touchpoint 3 (channel: ___) → installs: [identity — "you are the kind of person who…"] → ask present? NO
Touchpoint 4 (channel: ___) → installs: [permission] → ask present? NO
THE ASK → deferred to: [touchpoint #] → fires only after permission is live; phrased as the recipient's own next obvious step
```

Install belief before identity, identity before permission, permission before the ask. Two rapport accelerants belong in the early touchpoints and install belief/identity with no ask in sight: **(1) a vulnerable admission others would be embarrassed to make** (the fastest trust accelerant), **(2) genuine ignorance + fascination about a thing the target prides themselves on knowing.** Rapport and warmth are byproducts of this sequence — *"rapport is a byproduct of that"* — never engineer them as outcomes.

### Step 6 — Run the Defense / Ethics Gate (5 tests, BLOCKING — with the deterministic backstop)

This is the single non-negotiable of the domain, faithful to Hughes's Plato's-Cave stance: teach offense and defense as one act, and admit knowing the technique does not immunize you (*"a good well-informed victim"*). Every spec passes all five before Section 6's verdict can read PASS. **Any single FAIL blocks the spec.** Defense and positive-deployment notes must be sharper, not softer, than the offensive mechanic — the interrogation cluster and the FEAR "positive deployment" are exactly where optimism launders an exploitative mechanic, so police those hardest.

- **Test 1 — Name the technique honestly.** Write the real mechanic in plain words, Hughes's real name where one exists (PCP, FEAR, COPE, SMRP, the five trust factors, emotional debt), the synthesis coinage marked where it is the extractor's (Upstream Engine, Evidence Dilemma, Pressure Mechanics, the wall map). If you cannot name it without flinching, that flinch is the finding. Euphemism is a FAIL.
- **Test 2 — Defensive mirror.** Run this exact spec on yourself. Could you detect it? At which touchpoint? Would you feel **manipulated** or **helped**? The tell of over-engineering is permission arriving without the recipient having reasoned to it — *"it just makes perfect sense"* is the signature. Mirror reads "manipulated" → BLOCK.
- **Test 3 — Surface test.** Would you defend this design if the target saw the full spec — category word, build order, deferred ask — on the table? If it only works while hidden, it fails.
- **Test 4 — Outcome-on-merits.** Strip the engineered receptivity. Judging the end-state cold, does it genuinely serve the target? If it only serves them *because* it felt natural, the naturalness was the product — BLOCK.
- **Test 5 — Destabilization check.** The bright line. **Reducing existing chaos + supplying genuine clarity = help. Manufacturing chaos to sell the cure = BLOCK.** Read directly off Step 3's force-map: if the design adds a FEAR loop, manufactures an enemy, or fractionates the audience into a buying state, it is selling the cure for a disease it caused. Do not be the cliff that makes them grab your branch.

**Consent / power-asymmetry caveat:** if any touchpoint touches SMRP, the alternative question, the bait/Evidence-Dilemma question, or the punishment question, free exit is a precondition for PASS — running shame-dissolution on someone who cannot leave (employee, subordinate, partner mid-conflict) tips benevolent into coercive regardless of intent.

**The gate cannot be a thing the persona merely remembers to run** — that is the banned AI-memory-dependent observability pattern, which silently no-ops the first time the model is busy. The persona supplies the judgment (Tests 2, 3, 4, and the human read of Test 5); the deterministic primitive supplies the receipt and the structural floor. Run it on the spec file:

```bash
// turbo
python3 execution/context_ethics_gate.py check --file <spec-path> --kind spec --workflow ce-build --technique "PCP + Upstream Engine condition-chain + recipient-build sequence"
# exit 2 = BLOCK (halt + rewrite the flagged touchpoint, do NOT ship); REVIEW = persona must clear the named flags before PASS; PASS = proceed to handoff
```

This is the deterministic floor *under* the persona's Defense/Ethics judgment. It logs every PASS/BLOCK with the named technique and scans for the structural FAIL signatures — a category-escalation word with no verdict, an ask appearing in Step 5 before the permission rung, a force-map marking a FEAR loop PRESENT while the design adds one, an interrogation-derived spec with no free-exit declaration. Because it logs unconditionally, a missing verdict is itself a logged failure: the gate cannot silently no-op.

### Step 7 — Set the Followability Delivery State (Section 7)

The spec is inert until someone delivers it, and delivery is where authority is won or destroyed. *"Our brain's shortcut is that we follow someone who is probably loudest, clearest, and has no hesitation in their behavior… micro hesitations are the fastest way to destroy authority."* Specify:

- **State to speak FROM** — you induce the state you broadcast from. Speak from genuine confidence (its two real elements: **willingness to receive social injury** + a **fuzzy belief things work out okay**), not insecurity, not hierarchy/status thinking (which *"pushes your awareness back behind your eyes"*). Cue word: *"Forward."*
- **Hesitation kills** — flag every micro-hesitation, hedge, or apology in the assets and cut it. (Followable ≠ correct — keep the two axes split.)
- **Grade level** — write low. Lower-grade-level speakers win debates more often: *"I think like 35%"* (carry Hughes's hedge; write low anyway).
- **Picture-painting** — the message must paint a picture. Abstract = forgettable = unfollowed.
- **Gratitude / discipline cues** — present-moment thankfulness reads as emotional stability; visible (not performed) discipline reads as trustworthy.

### Step 8 — Produce the Build / Handoff Plan (which expert writes each piece)

The spec is a brief, not the assets. For each touchpoint in Step 5, name the production expert it routes to and the format they produce. The category word, the permission statement, and the recipient-build order are the constraints they write *into*. Validate every named partner against the live roster before routing — phantom routing is a failure.

Confirmed in-roster stacking partners: **Luke Iha** (line-level copy craft inside the designed context), **Lara Acosta** (LinkedIn posts), **`/caleb-4c-intro`** (cold-audience video front-end), **`/mcraney-deep-canvass`** (belief-change open, structurally identical to recipient-building), **`/drk-identity`** (identity install), **Connelly / `/connelly-subtext`** (component placement, no stated conclusion), **`/hughes-feel-clever`** (line-level engineered-self-conclusion inside the context this spec built), **`/supercomputer`** (multi-deliverable carry: anchor memory + cost gate across the assets). Then run `finalize` on the spec — Section 6's verdict is an input to `finalize`, not a substitute for it.

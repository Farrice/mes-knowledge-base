# PDP Rebuild Skill System Contract

## Evidence and objective

- **Source package:** `extractions/video-context/fwv1l_kdW18/`
- **Existing owner:** `skills/bitbranding-fashion-shopify/`
- **Gap closed:** the skill previously covered collection pages and product cards but explicitly excluded the product-detail page.
- **Behavioral objective:** turn verified apparel product and customer evidence into an objection-led PDP blueprint, then into a reviewable draft-theme mutation packet with explicit state, permission, and proof boundaries.
- **Non-objective:** autonomous store mutation, live-theme publication, universal Shopify documentation, or conversion guarantees.

## Components and composition

| Component | Role | Input | Output |
|---|---|---|---|
| `/bb-pdp-blueprint` | Evidence and architecture owner | product/customer/brand/constraint dossier | missing-facts register, objection ledger, module blueprint, copy/media/data requirements |
| `/bb-pdp-build-loop` | Safe implementation and review owner | approved blueprint + confirmed draft state | mutation packet or authorized mutation receipt, defect ledger, repair delta, QA and rollback state |
| `/bb-pdp-rebuild` | Front-door conductor | raw PDP rebuild request | phase-controlled run receipt and next safe action |
| BitBranding agent | Single function owner | apparel Shopify mission | routing, source boundary, handoffs, approval stops |

**Composition rule:** BitBranding owns the system. Brand strategy or copy specialists are optional inputs only when positioning or voice evidence is missing; they do not replace the PDP owner or widen the build.

## Execution order

1. Confirm apparel + Shopify fit and identify the exact product/template/theme.
2. Compile the dossier; label each field `VERIFIED`, `SOURCE-REPORTED`, `UNCONFIRMED`, or `MISSING`.
3. Ask only questions that change the architecture, claim safety, or implementation.
4. Approve the blueprint before producing any mutation instructions.
5. Confirm a uniquely named duplicated draft theme and explicit connector-write permission.
6. Re-read current draft state before every mutation or repair.
7. Inspect visually and functionally; record defects rather than trusting a success summary.
8. Stop before publication. Treat conversion, return-rate, and revenue effects as `UNTESTED` until an experiment produces receipts.

## Human checkpoints

- Missing product facts, policies, fit data, or authentic voice samples.
- Blueprint approval before implementation.
- Any Shopify connector write, even to a draft theme.
- Media selection, app-block placement, paid app choice, or custom-code escalation.
- Publication, traffic allocation, or A/B-test launch.

## Context policy

- Keep the existing skill cold-loadable; do not create a new global or hot skill.
- Load `genius.md`, the appropriate workflow, its v2 prompt, and the source package only when PDP work activates.
- Preserve collection-page mechanics; PDP mechanics are additive and local to this owner.
- Date connector-specific claims to the 2026-08-27 source and re-verify before real use.

## Validation and promotion

- Required: source-package verifier, skill audit, prompt-pointer wiring, command bridge, route discovery, and a cold-start fixture.
- Behavior proof: the fixture must reject a one-shot “make it premium” input, surface missing facts, produce an objection-led blueprint, and stop at the external-write boundary.
- Promotion ceiling: durable local skill expansion. No enforcement gate or autonomous connector action without three production receipts, a frozen negative control, and explicit approval.

## Agentic Engineering Packet

### System objective

Preserve the source's full evidence → blueprint → isolated mutation → inspect → repair loop while keeping product truth, store state, and permissions explicit.

### Source of truth

- Primary: local video-context package and mastery extraction.
- Implementation owner: existing BitBranding skill and agent.
- Store truth during a real run: current Shopify draft theme plus verified product/admin records; never a stale transcript-derived theme map.

### Context engineering plan

- **Chunk 1:** Dossier and status labels.
- **Chunk 2:** Objection ledger and module order.
- **Chunk 3:** Approved blueprint and exact build delta.
- **Chunk 4:** Current draft state, inspection evidence, and repair delta.
- **Review loop:** each chunk passes its own quality gate before the next one can mutate or reinterpret it.

### Dependency gate

No new dependency is required. The workflows prepare connector-ready artifacts; actual connector availability and permissions are discovered at run time.

### Use-now artifact

The cold-start fixture and three v2 prompts are usable without a Shopify connection. They prove route and output behavior locally.

### Hardening path

After explicit authorization and a real draft-theme run: retain before/after state, device screenshots, defect ledger, rollback result, performance receipt, and experiment plan. Only those receipts can support broader automation or promotion.

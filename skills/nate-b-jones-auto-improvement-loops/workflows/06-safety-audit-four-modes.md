# 4-Mode Safety Audit

> Load `genius.md` first. "The relevant safety concerns when we're talking about autoimproving agents in the business context are not really intelligence explosions. They're about failure modes that are quiet and specific and very easy to miss."

## Pre-Flight Gate

All 4 failure modes require explicit detection + response mechanisms. No exceptions. "Silent degradation is the most insidious."

## When to Use

- Pre-production for any auto-improvement system
- Post-incident review (which failure mode occurred?)
- Quarterly audit of existing loops
- Before graduating to customer-facing systems (WF 07 promotion gate)

## Execution

### Failure Mode 1 — Metric Gaming

**What it is**: Agent optimizes a proxy metric that diverges from actual business value. "Fraud model scores great in tests, misses actual fraud." "Pricing agent maximizes defined metric while killing customer trust."

**Detection mechanisms**:

1. **Held-out benchmark tasks** (Pattern 8 from WF 05)
   - 15-20% of benchmark rotated per cycle
   - Gaming flag: seen_score - held_out_score > 1.5
   
2. **Out-of-distribution probes**
   - Quarterly run of tasks drawn from outside the benchmark distribution
   - Flag: significant score delta between in-distribution and OOD

3. **Business-value correlation tracking**
   - Actual downstream metric (revenue, conversion, accuracy on ground truth) vs benchmark score
   - Flag: benchmark score rising while business metric stagnant or declining

**Response mechanisms**:
- Gaming flag → auto-DISCARD variant
- 2+ gaming flags in 10 cycles → pause evolution, investigate rubric + data
- Business-correlation break → reassess metric definition (GP-13 violation)

**Monitoring cadence**: every cycle (held-out), quarterly (OOD), weekly (business correlation)

### Failure Mode 2 — Silent Degradation

**What it is**: Subtle policy drifts, quality erosion persisting undetected because monitoring wasn't designed for autonomous edits.

**Detection mechanisms**:

1. **Regression benchmark suite**
   - Golden-set of canonical tasks the system should NEVER regress on
   - Runs every N KEPT cycles (default N=5)
   - Flag: any regression >0.5 on golden set

2. **Quality baseline comparison**
   - Sampled outputs compared to pre-evolution baseline
   - Human-reviewed (sample size: 10 outputs per month)
   - Flag: qualitative degradation reported by reviewer

3. **Consistency checks**
   - Same input submitted multiple times
   - Flag: variance > threshold across identical inputs

4. **Tone/register monitoring** (for content systems)
   - Style fingerprint comparison to baseline
   - Flag: fingerprint drift > threshold

**Response mechanisms**:
- Regression flag → rollback last KEPT variant, investigate
- Quality drift → pause evolution, add new failing task to benchmark
- Consistency failure → investigate for non-determinism introduced by variant

**Monitoring cadence**: every 5 KEPT cycles (regression), monthly (human review), continuous (consistency)

### Failure Mode 3 — Contamination

**What it is**: Optimization loop influences the data it's evaluated against. The eval set becomes training signal. Reliability collapses.

**Detection mechanisms**:

1. **Data isolation verification**
   - Benchmark tasks NEVER appear in variant generation context
   - Held-out tasks NEVER visible to meta-agent until post-evaluation
   - Source data traceability: every benchmark task has origin-log (where did it come from? how was it generated?)

2. **Eval independence audit**
   - Quarterly: trace back each benchmark task to origin
   - Flag: any task that was generated by the system being optimized
   - Flag: any task whose answer was seen by the variant in training/context

3. **Cross-contamination checks**
   - If multiple auto-improvement loops exist, verify their eval sets are isolated
   - Flag: shared benchmark across loops

**Response mechanisms**:
- Contamination flag → immediately exclude contaminated tasks
- Compromised eval → rebuild benchmark from clean sources
- Systemic contamination → pause all loops, full audit

**Monitoring cadence**: continuous (isolation), quarterly (origin audit)

### Failure Mode 4 — Compounding Errors

**What it is**: Bad optimization in one system cascades into interconnected business processes. "Pricing optimization breaks recommendations. Recommendations break retention."

**Detection mechanisms**:

1. **Cross-system impact tracking**
   - Map downstream dependencies for each auto-improvement system
   - Monitor downstream metrics for correlation with variant KEEP events
   - Flag: downstream metric degradation coincident with KEEP

2. **Canary deployment**
   - KEPT variants deploy to small traffic slice first (5%)
   - Full traffic after 24-48h with no downstream issues
   - Flag: downstream alert during canary → rollback

3. **Dependency regression suite**
   - Golden-set tasks that exercise downstream systems
   - Flag: downstream golden-set regression

**Response mechanisms**:
- Canary alert → auto-rollback
- Downstream correlation → pause affected loop, investigate dependency
- Systemic cascade → pause all loops, incident response

**Monitoring cadence**: continuous (canary), weekly (dependency regression)

### Phase 5 — Human Inspection Gates

Mandatory human inspection points (GP-14):

| Gate | When | Who | Criteria |
|------|------|-----|----------|
| Promotion | KEPT variant → production deployment | Domain owner | Business-value review |
| Graduation | Internal → customer-facing | Director/VP | Full 4-mode audit pass |
| Incident | Any flag fires | On-call + domain owner | Root cause analysis |
| Monthly | Normal operation | Domain owner | Random trace sample review |
| Quarterly | Normal operation | Domain owner + safety lead | Full audit + metric review |

Human gates cannot be automated away (GP-14 violation risk).

### Phase 6 — Revert Protocol Verification

Test the full revert capability:

1. Make a change via the loop
2. Run 3 benchmarks
3. Revert the change
4. Run 3 more benchmarks
5. Verify: system returned to exact prior state (metric matches pre-change baseline)

Failure here = revert is broken = any flag is catastrophic. Fix before any production use.

## Content Type Adaptations

| System Type | Highest-Risk Failure Mode | Critical Detection |
|-------------|---------------------------|-------------------|
| Fraud detection | #1 Metric gaming | OOD probes (novel fraud patterns) |
| Pricing engine | #4 Compounding | Cross-system canary (affects conversion) |
| Content system | #2 Silent degradation | Tone/register fingerprint |
| Customer service | #1 + #4 | Business-value correlation + canary |
| Internal dev tool | #3 Contamination | Origin audit (was benchmark self-generated?) |
| Compliance workflow | #2 + #4 | Golden-set + cross-system canary |

## Output Requirements

- 4-mode audit document
- Per-mode detection + response + cadence
- Human inspection gate schedule
- Revert protocol test results
- Composite safety score
- Deployment recommendation

## Quality Gate

- **Safety Monitoring** (0-10): all 4 modes have detection AND response?
- **Revert Capability** (0-10): test passed for full-cycle revert?
- **Judgment Leverage** (0-10): human gates defined and owned?

Minimum: 8 on each for customer-facing; 7 for internal.

## Anti-Patterns

- ❌ "Silent degradation hasn't happened to us" (it has — you just haven't detected it)
- ❌ Gaming detection only on unseen tasks (meta-agent finds held-out tasks eventually; rotate!)
- ❌ No canary for downstream-impacting changes
- ❌ Auto-promotion without human gate
- ❌ Revert "untested because it would be disruptive" (broken revert is catastrophic — TEST)

## Role & Activation

You are running the safety audit the way Nate B Jones scopes the risk of self-improving business agents: "The relevant safety concerns when we're talking about autoimproving agents in the business context are not really intelligence explosions. They're about failure modes that are quiet and specific and very easy to miss." All four failure modes — metric gaming, silent degradation, contamination, compounding errors — require explicit detection AND response mechanisms. "Silent degradation is the most insidious" is not a rhetorical flourish; treat it as the mode most likely to be under-audited by a team that feels confident. No exceptions on coverage: an audit that skips a mode because "that hasn't happened to us" has already failed.

## Input Required

- **[ARCHITECTURE]** — the meta/task architecture from the architecture-design workflow
- **[TRACE INFRASTRUCTURE]** — the trace system already in place
- **[AFFORDANCES]** — pre-loaded patterns, especially held-out benchmark (Pattern 8) and rubric randomization (Pattern 9)
- **[PRODUCTION SCOPE]** — the production system this loop will eventually touch, and its blast radius

## Execution Protocol

### Failure Mode 1 — Metric Gaming
Definition: the agent optimizes a proxy metric that diverges from actual business value. Detection mechanisms: (1) held-out benchmark tasks — 15-20% rotated per cycle, gaming flag when seen_score minus held_out_score exceeds 1.5; (2) out-of-distribution probes — quarterly run of tasks drawn outside the benchmark distribution, flag on significant in-distribution vs OOD score delta; (3) business-value correlation tracking — the actual downstream metric (revenue, conversion, ground-truth accuracy) plotted against benchmark score, flag when benchmark score rises while the business metric stagnates or declines. Response: gaming flag → auto-DISCARD the variant; 2+ gaming flags in 10 cycles → pause evolution, investigate rubric and data; business-correlation break → reassess the metric definition itself (this is an outcome-vs-activity failure, not just a tuning problem). Monitoring cadence: every cycle (held-out), quarterly (OOD), weekly (business correlation).

### Failure Mode 2 — Silent Degradation
Definition: subtle policy drift or quality erosion that persists undetected because monitoring wasn't designed to catch autonomous edits. Detection mechanisms: (1) regression benchmark suite — a golden-set of canonical tasks the system should never regress on, run every N KEPT cycles (default N=5), flag on any regression exceeding 0.5 on the golden set; (2) quality baseline comparison — sampled outputs compared to pre-evolution baseline, human-reviewed at 10 outputs/month, flag on any qualitative degradation the reviewer reports; (3) consistency checks — same input submitted multiple times, flag if variance across identical inputs exceeds threshold; (4) tone/register monitoring for content systems — style fingerprint compared to baseline, flag on drift exceeding threshold. Response: regression flag → rollback the last KEPT variant, investigate; quality drift → pause evolution, add the new failing case to the benchmark; consistency failure → investigate for non-determinism introduced by the variant. Monitoring cadence: every 5 KEPT cycles (regression), monthly (human review), continuous (consistency).

### Failure Mode 3 — Contamination
Definition: the optimization loop influences the data it's evaluated against — the eval set becomes training signal and reliability collapses. Detection mechanisms: (1) data isolation verification — benchmark tasks never appear in variant-generation context, held-out tasks never visible to the meta-agent until post-evaluation, every benchmark task has an origin-log; (2) eval independence audit — quarterly trace-back of each benchmark task to its origin, flag any task generated by the system being optimized or whose answer was seen by the variant in training/context; (3) cross-contamination checks — if multiple auto-improvement loops exist, verify their eval sets are isolated, flag any shared benchmark across loops. Response: contamination flag → immediately exclude the contaminated tasks; compromised eval → rebuild the benchmark from clean sources; systemic contamination → pause all loops, run a full audit. Monitoring cadence: continuous (isolation), quarterly (origin audit).

### Failure Mode 4 — Compounding Errors
Definition: bad optimization in one system cascades into interconnected business processes — pricing optimization breaks recommendations, recommendations break retention. Detection mechanisms: (1) cross-system impact tracking — map downstream dependencies for each auto-improvement system, monitor downstream metrics for correlation with variant KEEP events, flag downstream degradation coincident with a KEEP; (2) canary deployment — KEPT variants deploy to a small traffic slice (5%) first, full traffic only after 24-48h with no downstream issues, flag → rollback if a downstream alert fires during canary; (3) dependency regression suite — golden-set tasks that exercise downstream systems, flag on downstream golden-set regression. Response: canary alert → auto-rollback; downstream correlation → pause the affected loop, investigate the dependency; systemic cascade → pause all loops, run incident response. Monitoring cadence: continuous (canary), weekly (dependency regression).

### Human Inspection Gates
Specify the mandatory human gates (these cannot be automated away): Promotion (KEPT variant → production, owner: domain owner, criteria: business-value review); Graduation (internal → customer-facing, owner: director/VP, criteria: full 4-mode audit pass); Incident (any flag fires, owner: on-call + domain owner, criteria: root cause analysis); Monthly (normal operation, owner: domain owner, criteria: random trace sample review); Quarterly (normal operation, owner: domain owner + safety lead, criteria: full audit + metric review).

### Revert Protocol Verification
Test — do not assert — the full revert capability: make a change via the loop, run 3 benchmarks, revert the change, run 3 more benchmarks, verify the system returned to exact prior state (metric matches pre-change baseline). A revert "untested because it would be disruptive" is not acceptable — a broken revert is catastrophic precisely because it's discovered only when needed.

## Output Contract

- 4-mode audit document, each mode with detection mechanisms, response mechanisms, monitoring cadence, and current flag status
- Human inspection gate schedule (all 5 gates, owner + criteria)
- Revert protocol test results (actual test run, not asserted capability)
- Composite safety score (per-mode + overall)
- Explicit deployment recommendation: APPROVED FOR PRODUCTION / CONDITIONAL / BLOCKED

## Quality Gate

- Does every one of the 4 failure modes have BOTH a detection mechanism AND a response mechanism specified — no mode with detection-only or response-only?
- Is the held-out benchmark's data-isolation requirement explicit for Failure Mode 3 (held-out tasks never visible to the meta-agent pre-evaluation)?
- Was the revert protocol actually tested (3 benchmarks, change, revert, 3 more benchmarks) rather than assumed working?
- Are minimum thresholds respected — 8/10 per mode for customer-facing systems, 7/10 for internal — with the deployment recommendation matching the actual scores?
- Does the deployment recommendation land on one of the three named states (APPROVED / CONDITIONAL / BLOCKED), never left implicit?

## Deploy When

- Pre-production gate for any auto-improvement system before it touches anything beyond a sandbox
- Post-incident review to identify which of the 4 modes actually occurred
- Quarterly audit of an existing loop already in production
- Before graduating a system from internal to customer-facing (the graduation gate itself)
